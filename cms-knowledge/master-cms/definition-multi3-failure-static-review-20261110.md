# MULTI3 문서694 실패의 정적 비교 검토

작성일은 2026-11-10입니다. 원본430/529/530, 이전 성공 QA661의 입력 ZIP, 실패한 MULTI3 ZIP을 읽어 비교했습니다. 원본·fixture·기존 보고서는 수정하지 않았으며 이번 작업에서는 새 보고서만 작성했습니다. 브라우저·네트워크·CMS API·전역 인덱스를 조작하지 않았습니다. 실행 근거2661~2667은 이미 저장된 로컬 JSON으로만 읽었습니다.

정적 검사에서 ZIP 손상, JSON 문법 오류, 파일명과 masterId 불일치, 명백한 Int32 초과는 발견하지 못했습니다. 실패 원인은 확정할 수 없습니다. 이전 성공 QA661과 비교해 새로 달라진 축은 멤버 수와 유형 구성, questionId/masterId 관계, 표지 HTML, ZIP 멤버 시각 등이며, 이 차이들을 서로 분리한 실행은 아직 없습니다.

## 1. 실행 관측과 파일의 연결

[2661](evidence/2661-definition-multi3-register-submit-once.json)의 저장된 결과는 `attemptCount=1`, `submitClicked=true`, 파일명 `QA-DIFI-20261110-04-MULTI3.zip`, SHA-256 `e53927cb286a91f50353b2f55b2dc8ff7d9c38a7d66fa8e606aa97a240f58171`을 기록합니다. 이 SHA는 이번에 읽은 로컬 MULTI3 파일과 일치합니다. [2662](evidence/2662-definition-multi3-register-post-observation.json)와 [2663](evidence/2663-definition-multi3-submit-reconcile.json)은 제출 후 관측과 목록 전환을 기록합니다.

[2664](evidence/2664-definition-multi3-list-readback.json)의 목록 행은 문서694, 해당 파일명, 출처 `22-M-MA-T0-1-1-SMT-TP-2022`, 중학1·1학기, 실패 상태를 표시합니다. 같은 목록에는 이전 QA661이 승인 상태로 표시됩니다. QA661을 과거 성공 입력으로 삼는 것은 상위 조사자의 실제 등록 관측을 전제로 하며, 과거 성공이 현재 서버 환경의 동시 대조 실험이라는 뜻은 아닙니다.

[2665](evidence/2665-definition694-failed-detail-open.json), [2666](evidence/2666-definition694-failed-detail-source.json), [2667](evidence/2667-definition694-failed-detail-observation.json)의 상세에는 다음 두 문구가 함께 존재합니다.

- 상단: `ZIP 파일 자체에 오류가 있어 파싱을 시작하지 못했습니다.`
- 문항 없는 영역: `HML 파일 자체에 오류가 있어 파싱이 시작되지 못했습니다.`

표시된 생성 문항은0개입니다. 이 문구는 화면에서 확인한 실패 분류이며, ZIP 라이브러리 단계·JSON 역직렬화 단계·외부 ID 검증 단계·문항 변환 단계 중 어디서 실패했는지를 보여 주는 스택 트레이스는 아닙니다. 하단의 HML 표기만으로 HML 파서가 실제 실행되었다거나 잘못된 엔드포인트로 전송되었다고 단정할 수 없습니다. 문구 재사용이나 오류 분기 혼용 가능성도 서버 구현을 보지 않고는 확정할 수 없습니다.

상위 조사자는 별도로 문서694에서 다운로드한 파일의 SHA도 로컬 MULTI3와 일치한다고 전달했습니다. 이 하위 작업은 재다운로드하지 않았습니다. 또한 상위 조사자가 PUT 로그 행을 발견하지 못한 사실은 미관측으로 기록하며, 서버 내부 쓰기나 외부 ID 예약이 없었다는 증거로 바꾸어 해석하지 않습니다.

MULTI3의 숫자 ID12개는 서로 다르고 모두 양의 정수입니다. 가장 큰 값2116111034는 Int32 최댓값2147483647보다31372613 작습니다. QA661도 같은21억대 숫자를 사용했으므로 단순한 자리 수 증가나 명백한 signed Int32 초과는 현재 파일에서 확인되지 않습니다. masterId는 모든 원본과 QA 입력에서 문자열이며 나머지 세 ID는 정수입니다. JSON 숫자를 부동소수점 정밀도 한계 때문에 잃을 정도의 크기도 아닙니다.

QA661은 questionId와 masterId의 숫자 값 및 파일명 stem이 모두 같습니다. MULTI3는 파일명 stem과 masterId는 같지만 questionId는 다릅니다. 그러나 실제 원본 세 개도 questionId와 masterId가 다르므로 원본 형식 전체에 두 ID의 동일성을 요구하는 규칙이 있다고 단정할 수 없습니다. 현재 등록 경로가 과거 원본 생성 경로와 다른 내부 검증을 쓰는지는 미확정입니다.

ID가 정수 범위 안에 있다는 사실은 서버의 업무상 ID 범위·중복·예약 정책까지 증명하지 않습니다. 기존 다른 문서와의 충돌이나 실패 단계의 외부 ID 예약 여부는 이 정적 파일 비교로 알 수 없습니다.

## 4. 인코딩·JSON·내용 보존

모든 JSON을 엄격한 UTF-8로 디코딩하고 중복 키를 검사하며 파싱했습니다. 전부 BOM이 없고, 잘못된 UTF-8·중복 JSON 키·대체 문자 U+FFFD·고립 surrogate는 발견하지 못했습니다. UTF-16 파일이나 ZIP 바깥에 붙은 JSON도 아닙니다. 각 JSON은 최상위 객체이고 같은16개 키를 같은 순서로 담습니다. 줄바꿈 없는 compact JSON이며 CRLF와 LF는 모두0개입니다.

| JSON | 바이트 | 원본과 비교한 비ASCII 바이트 수 | JSON SHA-256 |
|---|---|---|---|
| QA661 ORDERED | 1855 | 원본530과 같은327 | `8637c51b9d422c165e45532e6606f099c53265bc7cddf35c64cd5c4fd2fc9acf` |
| MULTI3 ESSAY | 1730 | 원본430과 같은228 | `fa4297c0d54e0d7ced9e3bca5a72369a1be66ffef19140e9c808671462c02c44` |
| MULTI3 FIVE | 2129 | 원본529와 같은96 | `c0ac64210a205b523d5b94edaa8075ade3228f14bbac3fc13f03f786d76a7d73` |
| MULTI3 ORDERED | 1876 | 원본530과 같은327 | `6cdf8bbc740a71162dd38309d81b65553947b1408c198ab4891a6ffe6fe601db` |

원본에서 해당 MULTI3 문항으로 바뀐 leaf는 각 문항당 다음5개뿐입니다.

- `$.questionId`
- `$.masterId`
- `$.questionContent`
- `$.questionGrading.questionGradingId`
- `$.questionGrading.questionCorrects[0].questionCorrectId`

QA661과 MULTI3의 ORDERED를 직접 비교해도 차이는 같은5개 경로뿐입니다. 두 파일의 ID 네 값을 같은 값으로 놓고 각 QA 표지만 제거하면 나머지 JSON 객체가 완전히 같습니다. QA661의 표지는 `<p>[QA-DIFI-20261109-01]</p>`이고 MULTI3의 표지는 `<p><span>[QA-DIFI-20261110-04-ORDERED]</span></p>`입니다. 둘 다 기존 d-question 안에 추가되어 있습니다. 원본 본문에도 p/span 구조가 있지만, 추가 표지의 span 유무가 현재 파서에 영향을 주는지는 별도 실행하지 않았습니다.

따라서 문서 작성 때 발생했던 PowerShell 한국어 인코딩 문제가 MULTI3 문항 JSON을 손상했다는 근거는 없습니다. 원래 한국어·수식·HTML은 파일에서 직접 읽어 보존했으며 JSON 바이트 복원 검사도 통과했습니다. 자산 누락을 주장할 선언 리소스도 없습니다. 세 원본과 QA 모두 `questionResources=[]`이고 HTML 이미지 참조가 없습니다.

## 5. ZIP 로컬 헤더·중앙 디렉터리·플래그

| 항목 | 실제 원본430/529/530 | 성공 QA661 | 실패 MULTI3 |
|---|---|---|---|
| 압축 방식 | DEFLATE, method8 | 동일 | 동일 |
| create_system / create_version / extract_version | 0 / 20 / 20 | 동일 | 동일 |
| general purpose flags | `0x0808`（2056） | `0x0000` | `0x0000` |
| data descriptor | 있음 | 없음 | 없음 |
| 로컬 헤더 CRC·크기 | 0, 실제 값은 descriptor/central에 존재 | 실제 값 기재 | 실제 값 기재 |
| external_attr | 0 | 25165824 (`0x01800000`) | 동일 |
| internal_attr / volume | 0 / 0 | 동일 | 동일 |
| extra·파일 comment·ZIP comment | 모두 빈 값 | 동일 | 동일 |
| 암호화 플래그 | 없음 | 없음 | 없음 |
| filename 문자 | ASCII | ASCII | ASCII |

원본의 각 압축 데이터 뒤에는 실제 `PK 07 08` descriptor가 있고, 기록된 CRC·압축 크기·원본 크기가 중앙 디렉터리와 일치합니다. QA661과 MULTI3는 descriptor 없이 로컬 헤더에 값이 직접 기록되며 중앙 디렉터리와 일치합니다. 모든 멤버에서 실제 바이트로 CRC를 다시 계산해 일치함을 확인했고 `zipfile.testzip()`도 전부 통과했습니다.

ZIP 끝의 EOCD는 디스크0, 정상 멤버 수와 중앙 디렉터리 위치를 기록하며 뒤에 불필요한 바이트가 없습니다. 원본과 QA의 ZIP 구조가 바이트 수준에서 동일한 것은 아니지만, 성공 QA661과 MULTI3는 플래그·descriptor 방식·속성·버전에서 같은 계열입니다. 따라서 `flag_bits=0`이나 descriptor 부재를 단독 실패 원인으로 보는 근거는 약합니다. ZIP의 UTF-8 이름 플래그 차이를 JSON 본문의 실제 UTF-8 손상과 같은 문제로 취급해서도 안 됩니다.

이 검사로 표준 ZIP 도구에서 읽을 수 있는 무결성은 확인했지만, 서버의 사용자 정의 파일 선택 규칙·멤버 수 제한·ZIP 전체 크기 제한까지 통과한다고 증명하지는 않습니다.

JSON 내부의 attribute·문항·그레이딩·정답 날짜는 해당 원본에서 변하지 않았습니다. QA661과 MULTI3 ORDERED의 모든 내부 날짜도 같습니다. 모두 `lastModifiedDtmAtLinks="-999999999-01-01T00:00:00"`를 사용하므로 이 특수 연도 문자열만을 일반적인 파싱 실패 원인으로 지목하기는 어렵습니다. ESSAY의 그레이딩 수정 시각과 문항 수정 시각 차이도 원본 그대로입니다.

## 8. 확정·추정·미확정의 구분

### 확정한 사실

- 제출 시 기록된 SHA와 로컬 실패 fixture의 SHA가 같습니다. 문서694의 실패·문항0개와 상단 ZIP/하단 HML 문구는 로컬 실행 근거에 존재합니다.
- ZIP·JSON의 정적 무결성 검사는 통과했습니다. 멤버명과 masterId가 같고 QA ID12개는 서로 다른 양의 Int32 범위입니다.
- 성공 QA661과 MULTI3의 주요 ZIP 플래그·압축 방식·인코딩은 같습니다. ORDERED 문항의 그 밖의 원본 내용도 같습니다.
- 실제 차이로는 멤버1개→3개, 첫 ESSAY와 유형 혼합, questionId/masterId 관계, 표지 p/span, ZIP 멤버 시각이 있습니다.

확정된 실패 원인은 없습니다. 위 목록은 확인한 사실과 단순 오류 후보를 배제한 범위입니다.

| 다중 JSON 처리 또는 유형 혼합·첫 ESSAY 처리 경로 | 성공 대조군은 단일 ORDERED, 실패 입력은 ESSAY부터3개입니다. | 멤버 수·유형·첫 멤버 효과가 함께 달라 개별 원인을 분리하지 못했습니다. | 우선 구분할 후보입니다. |

| ID 예약·중복 또는 입력 메타와 파서의 대응 | 업무상 검증은 정수 범위 검사와 별개일 수 있습니다. | UI 문항0개와 PUT 로그 미관측만으로 내부 상태를 판단할 수 없습니다. | 정적 비교로 우열을 정할 수 없습니다. |
| 표지 HTML의 추가 span | QA661과 ORDERED 사이에 남은 HTML 차이입니다. | 원본도 p/span을 쓰며 문법상 손상이나 내용 변경은 없습니다. | 낮은 우선순위의 미검증 후보입니다. |
| ZIP 멤버 시각 또는 사용자 정의 ZIP 요구사항 | QA661과 MULTI3의 날짜가 다릅니다. | 주요 헤더 방식은 성공 QA와 같고 CRC도 정상입니다. | 날짜 규칙을 보여 주는 근거가 없어 낮은 우선순위입니다. |

### 미확정으로 남는 사항

실제 서버 예외, ZIP 멤버를 선택하는 코드, JSON 객체 변환 시점, 유형별 지원 범위, 트랜잭션·예약·중복 정책, 현재 서비스 버전과 작업 실행 환경, 등록 메타의 적용·검증 순서는 확인하지 못했습니다. 하단 HML 문구가 코드 경로를 설명하는지 단순 표시 오류인지도 미확정입니다. 파일이 정적으로 정상이라는 사실과 현재 서비스에서 받아들여진다는 사실은 따로 검증해야 합니다.

## 9. 최소 구분 실험1개

후속 실험으로 MULTI3의 `2116111032.json`을 **바이트 그대로** 단독 ZIP에 넣는 방안을 제안합니다. JSON 바이트 수는1876이고 SHA-256은 `6cdf8bbc740a71162dd38309d81b65553947b1408c198ab4891a6ffe6fe601db`여야 합니다. 새 파일은 별도 이름을 사용하되 기존 fixture는 수정하지 않습니다. 이번 하위 작업에서는 실험 ZIP을 만들거나 등록하지 않았습니다.

JSON 내부의 ID·표지 p/span·날짜·그레이딩·타입과 멤버명 `2116111032.json`을 유지합니다. 압축 방식·플래그·속성·ZIP 멤버 DOS 시각도 현재 멤버와 같게 유지합니다. 실행 메타는 문서694와 같은 Source13, 단원20자 코드 `22MMAT0KOK1001020000`, 페이지1~3, 공통(C)로 고정하는 것이 부모의 현재 계획입니다. 그 코드나 페이지가 올바른 서버 정책이라는 뜻은 아닙니다.

외부 ID는 questionId2116111031, masterId문자열`"2116111032"`, grading2116111033, correct2116111034를 그대로 사용합니다. 새 ID가 필수라는 근거는 없습니다. 그대로 써야 실패 MULTI3의 동일한 JSON을 단독으로 시험한다는 조건을 지킬 수 있습니다. 다만 UI 문항0개는 문서694 처리 중 외부 ID가 내부에 예약되지 않았다는 증거가 아닙니다. 따라서 재사용 충돌 가능성은 남는 한계로 명시해야 합니다.

새 ID 네 개와 새 멤버명을 부여하면 잠재적인 충돌을 줄일 수는 있지만, 그때는 동일 JSON 바이트 실험이 아니며 성공·실패 해석에 ID 변경이라는 축이 추가됩니다. 원인 분리를 우선하는 이 최소 실험에서는 ID를 유지하고 재사용 사실을 기록하는 편이 적합합니다.

| 결과 | 좁힐 수 있는 범위 | 여전히 분리하지 못하는 범위 |
|---|---|---|
| 단독 ORDERED 성공 | 현재 환경에서 해당 JSON·ID 관계·표지·날짜·메타·단일 ZIP이 함께 수용됩니다. 실패가 단독 ORDERED 내용만의 필연적 문제라는 설명은 약해집니다. | 다중 멤버 수 제한, ESSAY/FIVE 개별 처리, 혼합·순서·전체 실패 정책은 서로 구분되지 않습니다. |
| 단독 ORDERED 실패 | 여러 멤버가 있어야만 실패한다는 설명만으로는 충분하지 않습니다. | 내용·ID 재사용/예약·현재 파서/작업 환경·메타를 분리하지 못하며, 과거 QA661 성공과 현재 환경 차이도 남습니다. |

이 실험은 문항 수와 유형 구성을 함께 줄이므로 한 번으로 다중 JSON 제한과 ESSAY 문제를 각각 확정할 수 없습니다. 실패 시 새 ID로 다시 시도하는 등의 추가 실험은 별도의 조건 변경이며 이 보고서에서는 실행하지 않았습니다.
